# Friday server

TypeScript + Fastify. ESP32 передаёт звук по WebSocket, сервер сразу пишет его на диск.
По слову «Пятница» начинается передача. Полторы секунды тишины или отпускание сенсора при ручной записи завершают WAV. Сервер распознаёт разговорную речь локально с Whisper small, сохраняя Vosk small RU 0.22 для точных команд увлажнителю, получает ответ Qwen 3.5 4B через Ollama и озвучивает его голосом Supertonic 3 F2.

## Запуск в терминале Codex

```sh
cd server
docker compose up -d --wait db
npm start
```

Открой [журнал обращений](http://localhost:33000/) на Маке. Для телефона используй
адрес Мака и порт из `.env`. Журнал показывает карточки во всю ширину,
подгружая более старые обращения при прокрутке. Доступны фильтры по устройству,
пользователю и диапазону даты/времени. Время вводится в часовом поясе браузера,
конечная минута включается целиком. Без фильтров видны обращения со всех устройств.
После завершения обработки, включая ошибки модели и синтеза, сервер посылает по SSE полную карточку
с устройством, пользователем и действиями. Подходящая запись добавляется или
обновляется без перезагрузки и прерывания плеера. После переподключения SSE
интерфейс сверяет загруженную часть истории с сервером.
Исходники интерфейса находятся в `web/src`. Команда `npm start` собирает
интерфейс и раздаёт его на одном порту с API.

Зависимости, Whisper small, Silero VAD и русская модель Vosk уже установлены в этой рабочей папке.
Сервер слушает **порт из `server/.env`** (по умолчанию `33000`) и печатает доступные IPv4-адреса Mac:

```text
ESP32 endpoint: ws://mac-host.local:33000/audio
● RECORD ...
WAV saved (6.08 s): .../recordings/....wav
Transcribing audio...
Transcript: Привет, это проверка записи звука.
```

Остановка: **Ctrl+C**. Закрытие соединения во время записи сохраняет неполный WAV.
При остановке сервера распознавание прекращается; уже сохранённые WAV остаются на диске.
После аварийного завершения процесса/отключения питания может остаться `.partial`;
такие файлы не считаются завершёнными и автоматически не распознаются.

ESP32 и Mac должны видеть друг друга в локальной сети. Если macOS запросит разрешение
входящих соединений для Node, разрешить его для этой сети. Сервер без авторизации,
предназначен для доверенной домашней сети; наружу в интернет его не публиковать.
Одновременно обслуживается одна ESP32. При переподключении новое соединение заменяет старое,
в том числе после перезапуска платы без закрытия TCP. Незавершённая старая запись сохраняется как неполная. Проверка доступности: `http://localhost:33000/health`.

## Линтинг, форматирование и Git-хук

Из папки `server`:

```sh
npm run lint       # Проверить форматирование, импорты и правила Biome
npm run lint:fix   # Применить безопасные исправления Biome
npm run format    # Только отформатировать файлы
npm run check     # Проверить типы TypeScript
```

Biome настроен в `biome.json` для исходников сервера, веб-панели, общих модулей,
скриптов, тестов и поддерживаемых файлов конфигурации/документации. Веса в
`server/models`, записи, зависимости, сборка веб-панели и lock-файл исключены.
Модули устройств в `src/services/smartHome/models` проверяются как обычный код.
Используется рекомендуемый набор правил. В тестовых фикстурах разрешены non-null
assertions; проверка убывания специфичности CSS отключена, поскольку она сравнивает
также селекторы независимых компонентов.

`npm install` / `npm ci` запускает `prepare`, который устанавливает Husky для этого
Git-репозитория. Для уже установленных зависимостей: `npm run prepare`.
Хук `server/.husky/pre-commit` запускает lint-staged: Biome форматирует и исправляет
подготовленные к коммиту файлы в `server`, а оставшиеся ошибки и предупреждения
блокируют коммит. Изменения форматирования попадают в индекс автоматически;
неподготовленные части файлов сохраняются отдельно. Прошивка не входит в эту проверку.
Проверка типов и тесты запускаются отдельно.

## Локальная LLM

На macOS Ollama работает отдельным нативным процессом с Metal; Docker нужен только для PostgreSQL.
Из папки `server` установи закреплённую версию CLI (архив проверяется по SHA-256):

```sh
npm run setup:ollama
npm run llm:serve
```

Оставь процесс работающим. В другом терминале, также из `server`:

```sh
npm run llm:pull
npm start
```

Модель по умолчанию — `qwen3.5:4b`. CLI хранится в `.tools/ollama`, веса в
`models/ollama`; оба каталога исключены из Git. Интернет нужен для скачивания.
Облачные функции Ollama отключены. Она слушает только `127.0.0.1:11434`.
Для другого установленного CLI можно задать `OLLAMA_BIN`.

Настройки `.env`: `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `LLM_TIMEOUT_MS` (по умолчанию 90000).
При смене модели выполни `npm run llm:pull`. API-клиент использует `POST /api/chat`,
включает thinking при передаче инструментов (бюджет 2048 токенов вместе с ответом).
Без инструментов thinking отключён и ответ ограничен 512 токенами. Контекст —
8192 токена, модель хранится в памяти 15 минут. Рассуждения не озвучиваются и не
попадают в журнал. Выбор команды с thinking медленнее, но в проверках Qwen 4B
без него путала устройства и подменяла настройки чтением состояния.
Незавершённый или пустой ответ считается ошибкой.

Контекст собирает сервер из журнала: до шести завершённых обменов за последние
30 минут одного `userId`, включая обращения с разных устройств, в пределах
6000 символов вместе с текущей фразой. Имя и идентификатор собеседника передаются
в системном сообщении. Распознавание личности по голосу пока не подключено:
используется зарегистрированный `userId` из сообщения устройства.

Вся речь проходит цепочку STT → LLM → инструменты (при необходимости) → TTS.
Ollama получает два инструмента: `get_device_state` и `set_device_power`.
Старые регулярные команды и отдельные файлы настройки увлажнителя больше не используются.
Интерфейс `LanguageModel` отделён от контекста диалога и поддерживает tool calling;
MCP пока не подключён. В журнале сохраняются источник ответа, модель,
длительность запроса, число токенов и ошибки. При сбое TTS текст ответа остаётся.
При сбое Ollama обращение завершается ошибкой, очередь продолжает обработку.
Звук ответа доступен в журнале; передача звука обратно на ESP32 пока не реализована.

## Файлы и распознавание

### Голосовое управление умным домом

Добавь приборы через **Умный дом** в хедере. Для установки зависимостей адаптеров
один раз выполни `npm run setup:home`: `uv` подготовит python-miio 0.5.12
(Python 3.11–3.12) и pysyncleo 0.4.1 с zeroconf 0.154.0 (Python 3.14).
Во время работы адаптеры запускаются с `--offline`; реквизиты передаются по stdin.

Поддержаны состояние и питание для Xiaomi Smart Humidifier 2 (`deerma.humidifier.jsq2g`),
Smartmi Fresh Air (`zhimi.airfresh.va2`/`va4`) и Ballu ONEAIR ASP-100 (RusClimate type 69).
Xiaomi работает по локальному miIO. Ballu находится по MAC из ссылки через mDNS
`_syncleo._udp.local.` и управляется по UDP; Mac и прибор должны находиться в одной
сети с доступным multicast. Qingping пока только в каталоге, адаптер ещё не подключён.

Примеры: «Включи бризер в родительской», «Выключи бризер в спальне Артёма»,
«Какое состояние увлажнителя в родительской?». Названия берутся из БД.
При нескольких совпадениях сервер ничего не выполняет и просит уточнить комнату/дом.
За одно обращение можно выполнить до восьми команд, например:
«Включи бризер и увлажнитель в родительской». Модель возвращает отдельный вызов
для каждого прибора; сервер выполняет их последовательно, отдельно проверяет
и записывает каждый результат. Ошибка одного прибора не мешает обработать остальные
и не отменяет успешные действия. Голосовой ответ содержит все результаты.
Целевая влажность, расписания и условные сценарии пока не поддерживаются.
Включение Ballu из выключенного состояния выбирает штатный ручной режим;
скорость и целевая температура не перезаписываются.

Для Ballu ASP-100 дополнительно доступны:

| Команда                        | Параметры и поведение                                                                               |
| ------------------------------ | --------------------------------------------------------------------------------------------------- |
| `set_ballu_mode`               | `manual`, `night`, `turbo` (15 минут), `eco` (пассивное проветривание)                              |
| `set_ballu_speed`              | Скорость 1–7; включает ручной режим                                                                 |
| `set_ballu_temperature`        | Подогрев приточного воздуха 5–25 °C, целое число; наличие нагревателя проверяется по ответу прибора |
| `set_ballu_button_sound`       | Звуки нажатий, `enabled`                                                                            |
| `set_ballu_backlight_auto_off` | Автоматическое гашение подсветки, `enabled`; не мгновенное управление светом                        |
| `set_ballu_sound`              | `off`, `rain`, `sea`, `forest`, `birds`, `fireplace`                                                |
| `reset_ballu_filter`           | Сброс счётчика основного фильтра по явной просьбе после обслуживания                                |

Примеры: «Включи ночной режим бризера в спальне Артёма», «Поставь третью скорость»,
«Задай подогрев 22 градуса», «Включи звук дождя». Указывай комнату при нескольких бризерах.
Эти настройки не применяются к Xiaomi. Во всех Ballu текущей установки датчики CO₂
отсутствуют: авторежим исключён из списка доступных команд.

`get_device_state` дополнительно возвращает режим, скорость, заданную и фактическую
температуру **приточного** воздуха, оставшееся время турбо, настройки звуков/подсветки,
код ошибки и сырое значение счётчика фильтра. Счётчик не называется процентом остатка:
источники расходятся в трактовке. В локальном профиле type 69 сброс передаётся
как `CmdExpendables(0)` и требует свежего подтверждения значения от прибора.

Отдельное включение/выключение нагрева, мгновенное гашение подсветки, отдельная
скорость ночного режима и сброс префильтра пока не подключены. Пятница не должна
заменять такие запросы похожими действиями. Режим eco не означает «выключить только нагрев».

После изменения настройки драйвер ждёт свежий ответ с нужным значением и только
затем сообщает успех. Если значение уже установлено, лишняя команда не отправляется;
сброс фильтра всегда требует нового подтверждения. Недоступные параметры и
неизвестная комплектация не считаются успешным выполнением.
Числовые значения передаются из фразы без округления и проверяются сервером:
например, запрос 30 °C вернёт уточнение диапазона 5–25 °C без обращения к прибору.
Готовую реплику инструмента сервер озвучивает напрямую без повторной генерации LLM.
Ошибки драйвера обезличиваются, токены не попадают в LLM-контекст или журнал.
Результат и выбранное устройство сохраняются в действиях обращения.
Модель видит каталог всех домов этой установки; разграничение прав пользователей
по домам пока не реализовано.

Логика приборов разделена по моделям в `src/services/smartHome/models/`:
`smartHumidifier2.ts`, `smartmiFreshAir.ts`, `balluAsp100.ts`. Каждый модуль задаёт
схему состояния, набор команд, схемы их параметров, проверку подтверждения и русские
описания состояния/результата. Общие команды состояния и питания собираются через
`models/common.ts` с конкретной схемой и описанием модели.

`registry.ts` собирает каталог возможностей и определения инструментов LLM из этих
модулей. Для нового прибора нужно добавить модуль и зарегистрировать его здесь;
при новой модели также нужна запись в каталоге БД и поддержка протокола в драйвере.
`executor.ts` выбирает устройство и команду, загружает данные подключения и ведёт
журнал. `driver.ts` выбирает Python-адаптер по транспорту (`miio`/`syncleo`), передаёт
параметры через stdin и возвращает ответ для проверки схемой модели.
Неожиданные ошибки кода/БД отмечаются как `internal_error`, известные ошибки
драйвера сохраняют свой код. Ошибка записи успешного результата в журнал не
переобозначается как недоступность прибора.

`npm run test:home` проверяет реальную Ollama на русских командах в изолированной
тестовой схеме с имитацией приборов — физические устройства не затрагиваются.
`npm run test:ballu` проверяет сериализацию UDP-команд и свежесть подтверждений
без сети; зависимости устанавливаются `npm run setup:home`.
Протоколы: [python-miio](https://github.com/rytilahti/python-miio),
[pysyncleo](https://pypi.org/project/pysyncleo/),
[Syncleo integration](https://github.com/DeKaN/ha-syncleo),
[ASP-100 parameters](https://github.com/he110/ha-rusclimate/blob/main/custom_components/rusclimate/api/params.py).

Подтверждённый ответ сервер озвучивает локально голосом **Supertone Supertonic 3 F2**
и сохраняет в `recordings/<дата>-<id>.reply.wav`. Путь появится в консоли.
Чтобы послушать любую реплику на Mac, выполни в папке `server`

```sh
npm run voice -- /tmp/friday-preview.wav "Привет! Я на связи."
afplay /tmp/friday-preview.wav
```

Для установки на новом компьютере распакуй архив в `server/models/`, сохранив
каталог `sherpa-onnx-supertonic-3-tts-int8-2026-05-11` внутри него.
[Архив модели F2 и остальных голосов](https://github.com/k2-fsa/sherpa-onnx/releases/download/tts-models/sherpa-onnx-supertonic-3-tts-int8-2026-05-11.tar.bz2)

### База данных

Из каталога `server` скопируй `.env.example` в `.env` и замени оба вхождения
`replaceWithLocalPassword` одним случайным паролем из букв и цифр.
Запусти `docker compose up -d --wait db`, затем `npm start`.
PostgreSQL 18 слушает локальный порт 55432 и сохраняет журнал в именованном томе.
Сервер применяет миграции при старте. Тесты используют отдельные временные схемы
в этой же базе. Начальная миграция создаёт первую ESP и профиль Кирилла.
Идентификаторы устройств, пользователей, обращений и действий имеют тип UUIDv7.
Для резервного копирования нужны база данных и каталог WAV.

### Схема умного дома

`Home → Room → HomeDevice`. Дом и комната имеют `displayName`; устройство
имеет `displayName`, обязательные `roomId` и `typeId`, а также `registrationData`
в JSONB. Дом устройства определяется через комнату, без дублирующего `homeId`.
Все идентификаторы — UUIDv7. Комнаты в разных домах могут называться одинаково.
Удалить дом с комнатами, комнату с устройствами или используемый тип нельзя.

`HomeDeviceType` — фиксированный каталог моделей. Поля: стабильный `code`,
отображаемое имя, производитель, модель, категория (`humidifier`, `airMonitor`,
`breezer`) и `registrationType`. Каталог заполняется миграцией:

| Модель                    | Код                         | Регистрация      |
| ------------------------- | --------------------------- | ---------------- |
| Xiaomi Smart Humidifier 2 | `xiaomi-smart-humidifier-2` | `miioToken`      |
| Qingping Air Monitor Lite | `qingping-air-monitor-lite` | `miioToken`      |
| Xiaomi Smartmi Fresh Air  | `smartmi-fresh-air`         | `miioToken`      |
| Ballu ONEAIR ASP-100      | `ballu-oneair-asp-100`      | `hommynShareUrl` |

Раздел **Умный дом** в хедере (`/smart-home`) позволяет создавать дома, комнаты
и устройства. Выбор дома сохраняется в URL; данные сохраняются в PostgreSQL.
Выбор модели определяет `registrationType` и поля подключения.
Форматы `registrationData`:

```json
{ "ip": "192.168.1.12", "token": "0123456789abcdef0123456789abcdef" }
```

```json
{ "shareUrl": "rusklimat://device-share/rusclimate/69/aabbccddeeff?token=example" }
```

Схемы Zod находятся в `src/services/validation/homeDevice.ts`.
`createHomeDevice` в `src/services/smartHome/devices.ts` берёт способ регистрации
из каталога, проверяет соответствующий JSON и создаёт запись. Ответ функции
не содержит реквизитов подключения. БД дополнительно проверяет связи,
непустые имена и то, что JSON является объектом; проверка полей JSON выполняется
в сервисе. Будущие операции изменения реквизитов должны использовать тот же валидатор.

`GET /api/smart-home` возвращает дерево домов и каталог моделей без реквизитов.
`POST /api/smart-home/homes`, `/rooms` и `/devices` создают соответствующие записи.
Имена ограничены 120 символами. На этом этапе формы сохраняют реквизиты;
проверка связи выполняется при запросе состояния или голосовой команде.

Запись в каталоге задаёт форму регистрации и не означает проверенную поддержку
каждой аппаратной ревизии. Для Qingping и Smartmi точные идентификаторы и доступность
miIO ещё нужно проверить при подключении. Эта миграция не подключает приборы,
не создаёт дома, комнаты или семь экземпляров устройств автоматически.

Существующая таблица `devices` остаётся каталогом голосовых терминалов ESP32.
Приборы умного дома хранятся отдельно в `homeDevices`; их регистрационные данные
содержат секреты и не должны попадать в списки устройств, журнал действий или контекст LLM.

### Записи

- `recordings/<дата>-<id>.wav` — исходный поток: mono PCM16, **20 кГц** в потоковом режиме и **16 кГц** в режиме записи в RAM.
- Рядом сохраняется `.txt` с распознанным текстом.
- `.incomplete.wav` — разрыв соединения, потеря кадров, таймаут или отмена; не распознаётся.
- Записи и модель исключены из Git. Автоматической очистки записей нет.
- По умолчанию используется `ASR_ENGINE=whisper`: Whisper small с Metal на Apple Silicon распознаёт всю речь, включая команды устройствам.
  Для потоковых записей Whisper преобразует звук с 20 до 16 кГц через встроенный miniaudio.
- Silero VAD выделяет речевые участки перед Whisper с запасом 150 мс по краям. Это уменьшает ложные расшифровки шума и тишины. Случайные повторы декодирования с повышением температуры отключены (`-nf`).
- Для простоты модель загружается при каждом распознавании. Очередь последовательная,
  максимум четыре задания с учётом текущего. Приём следующей записи работает во время распознавания.
- На одну запись — максимум 120 секунд; отсутствие аудио 10 секунд завершает её как неполную.
- Ошибка распознавания не удаляет WAV. Звук не уходит в облако, API-ключи не нужны.

Настройки при необходимости:

```sh
ASR_ENGINE=whisper WHISPER_LANGUAGE=ru npm start
# Автоматическое определение языка:
ASR_ENGINE=whisper WHISPER_LANGUAGE=auto npm start
```

При необходимости Vosk доступен как альтернативный движок через `ASR_ENGINE=vosk`. Гибридный режим со специальными командами удалён.
Также поддерживаются `WHISPER_BIN` (путь к whisper-cli), `WHISPER_MODEL` (путь к модели) и `WHISPER_VAD_MODEL` (путь к модели Silero).
По умолчанию используются `.tools/whisper.cpp/build/bin/whisper-cli`, `models/ggml-small.bin` и `models/ggml-silero-v5.1.2.bin`.

## Установка с нуля

Для русской модели нужны Node.js 22+, npm, uv, curl и unzip. Из папки сервера:

```sh
npm ci
uv venv --python 3.11 .tools/vosk-env
uv pip install --python .tools/vosk-env/bin/python vosk==0.3.44
mkdir -p models
curl -fL https://alphacephei.com/vosk/models/vosk-model-small-ru-0.22.zip -o .tools/vosk-ru.zip
unzip -q .tools/vosk-ru.zip -d models
ASR_ENGINE=vosk npm start
```

Для основного движка выполни `npm run setup:whisper` и `ASR_ENGINE=whisper npm start`.
Скрипт собирает whisper.cpp **v1.8.2**, скачивает multilingual small (~465 МиБ) и Silero VAD (~865 КиБ),
не устанавливает ничего глобально. Интернет нужен только для первоначальной установки.
Источники: [whisper.cpp](https://github.com/ggml-org/whisper.cpp/tree/v1.8.2),
[модели](https://huggingface.co/ggerganov/whisper.cpp),
[Fastify WebSocket](https://github.com/fastify/fastify-websocket).

## Протокол `/audio`

1. Текстовый WebSocket frame:
   `{"type":"start","deviceId":"01a20858-a582-724b-950b-855d0dfa5bec","userId":"01a20858-a582-7fa5-b8a6-a8b5bccf8b4a","sampleRate":20000,"channels":1,"format":"s16le"}`.
2. Бинарные frames с PCM16 LE (чётное число байтов, до 8192 байт на сообщение).
3. При отпускании: `{"type":"end","samples":121600}` — точное суммарное число отсчётов.
4. При потере данных: `{"type":"abort"}`. Обрыв сокета также означает неполную запись.

Ответы: `started`, `saved`, `transcript`, `aborted`, `error`, `transcription_error`, `processing_error`.
`saved` означает успешно закрытый WAV; `transcript` приходит после распознавания.
Сервер сверяет число отсчётов, ограничивает размеры и длительность, пишет маленькие
блоки сразу на диск, не копит запись в RAM. Синхронные записи на диск используются
для сохранения порядка сообщений.

## Проверки без перепрошивки

```sh
npm run check
npm test
```

Тесты проверяют WAV-заголовок и содержимое, последовательные записи, отключение,
отмену, несовпадение числа отсчётов и неверный формат.

Проверка с настоящим Whisper на русской синтезированной фразе (macOS с голосом Milena):

```sh
say -v Milena -o /tmp/friday-speech.wav --file-format=WAVE --data-format=LEI16@20000 \
  'Привет. Это проверка записи звука. Сегодня мы учим маленькое устройство понимать русскую речь.'
npm run test:whisper -- /tmp/friday-speech.wav
```

Она поднимает временный сервер на свободном loopback-порту, передаёт аудио с темпом ESP32,
проверяет настоящий результат распознавания и удаляет временные записи.
Можно отправить свой PCM16 mono 16 или 20 кГц WAV в уже запущенный сервер:

```sh
npm run send:wav -- /absolute/path/voice.wav
```

Полная проверка с работающей Ollama и скачанной моделью:

```sh
npm run test:assistant -- /absolute/path/question.wav
```

Она использует настоящий STT, LLM и TTS, проверяет журнал и выдачу WAV через HTTP.
История хранится во временной схеме БД, тестовые записи удаляются после проверки.
Увлажнитель в этой проверке не подключается.

## Language boundaries

System identifiers, log prefixes and diagnostics are English. LLM system instructions,
tool/parameter descriptions, UI labels and spoken replies are Russian. JSON keys,
tool names and enum values remain stable English API identifiers. `shared/errors.ts` defines stable error codes and English messages;
`shared/userErrors.ru.ts` contains their Russian user-facing equivalents.
API errors return `{ code, message }`; the web UI selects safe Russian copy by code,
including a Russian fallback for network failures and unknown server responses.
Device failures store an English diagnostic in `error` and a separate Russian spoken
reply in `result.reply`. An unconfirmed device response is marked `confirmed: false`;
it does not prove that the physical action did not happen.
Technical JSON keys in the journal are English. UI labels, assistant replies and TTS
remain Russian. The system prompt explicitly requires Russian even when the user
requests another language. Clearly foreign text-only replies (letters but no Russian
characters) get one additional Russian reformulation call, without any tools. This
is recorded as `translate_reply`. A failed repair returns a fixed Russian message;
it never retries device commands. Numeric answers are allowed without repair.
This script check does not classify mixed-language text; the prompt still governs it.
Russian examples in prompts/tests and user-owned data
(names, transcripts and conversation history) are preserved verbatim.
Existing journal entries are not rewritten and no database migration is required.

Run `npm test`, `npm run check` and `npm run web:build` for contract checks.
`npm run test:home` checks the real Ollama model with simulated devices, including
Russian replies to Russian and English user requests. It never controls physical devices.
